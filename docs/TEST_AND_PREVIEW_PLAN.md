## 1. この文書の役割

本書は、どの不具合をどの試験で検出するかと、端末確認をどの節目でまとめるかの正本である。

次を原則とする。

- 自動試験だけでiPhone実機品質を保証しない
- 実機確認だけに頼り、同じ不具合を毎回手作業で探さない
- 各PRでは型、単体、物理、ブラウザ試験を通し、端末確認はGA開始時とRCへまとめる
- 端末固有のP0またはP1が疑われる場合だけ、対象を絞った例外確認を行う
- `main`への取り込みと正式公開を分ける
- 完成前のGitHub Pages確認URLを外部へ案内しない
- GitHub PagesのURLは公開であり、秘密環境ではないことを明示する
- 個人アカウント、ゲーム記録保存、外部分析がないことも試験対象にする

Pagesの権限、未告知運用、非個人設定の分離は[公開・プレビュー・安全運用計画](./DEPLOYMENT_AND_SECURITY_PLAN.md)を正本とする。

データ、アカウント、外部通信は[データ非保存・GitHub運用方針](./DATA_AND_HOSTING_POLICY.md)を優先する。

## 2. G1を二段階へ分ける

### G1-A: 技術基盤

目的:

- 依存関係を再現可能にする
- CIを作る
- ブラウザ試験を作る
- GitHub Pagesの未告知確認枠を安全に作る
- PixiJSと一つの更新ループを起動する
- 非個人設定とゲーム記録の境界を固定する

G1-Aではピンボール物理の品質を判定しない。

`planck`の版とlockの互換性を確かめるため、G1-Aでは最小の物理世界・動的body・1ステップだけの読込確認を行う。衝突や操作感の物理シナリオ試験はG1-Bから開始する。

### G1-B: ピンボール技術試作

目的:

- Planck.js
- 左右フリッパー
- 発射
- 安全ショット
- 入力キュー
- 接触処理
- 状態遷移
- 一回のゲーム状態をメモリ内だけに閉じること
- 外部通信とゲーム記録保存がないこと
をG1-Aの基盤上で検証する。

二本指、Safari固有挙動、体感遅延、発熱はGA開始時の端末確認へ引き継ぐ。

G1-Aを取り込む前にG1-Bへ進まない。

## 3. 試験の層

| 層 | 主な道具 | 確認対象 |
|---|---|---|
| 型・静的検査 | TypeScript、ESLint、typescript-eslint | 型、未使用、危険な依存、禁止API、禁止保存 |
| 単体試験 | Vitest | 状態遷移、入力所有、入力キュー、盤面検査、非個人設定 |
| 物理シナリオ試験 | Vitest + Planck.js | 壁抜け、接触順序、球受け、再配置、資源解放 |
| ブラウザ自動試験 | Playwright Test | 起動、画面、キーボード、Pointer Events、WebGL、再読込初期化、外部通信なし |
| 節目の端末確認 | iPhone、iPad | GA開始時とRCに、二本指、Safari、音声、発熱、画面高さ、体感遅延、設定保存なし動作をまとめて確認 |
| 試遊 | 未告知確認URLと試遊手順 | 理解、上達、公平感、中心体験 |

PlaywrightのWebKitはSafariそのものではない。差分は未確認事項として残し、節目の端末確認で扱う。

## 3.1 G3 / GA縦切りの自動確認

G3 / GAでは、G2仮図形を3球の一回のゲームへ接続する。自動試験で次を確認する。

- 球開始、球終了、次球、3球目の結果表示が順序どおりに進む
- 得点とショット進行は球間で保持し、コンボは球終了で解除する
- 新しいゲームで球数、得点、進行、結果、試遊レポートを初期化する
- レポートがゲーム開始、球開始、ショット成功、球終了、ゲーム終了を有限件数で保持する
- `localStorage`、`IndexedDB`、Cookie、URL、外部通信へゲーム記録を書かない
- Chromium / WebKitの起動、再読込、入力、安全停止を既存ゲートどおり確認する

PR #16後の操作因果パスでは、追加で次を確認する。

- 最大発射とフリッパーのPointer入力だけで`L0` / `R0`を完了できる
- 球の直接移動、速度の直接変更、成功イベントの直接生成を因果証明に使わない
- 60Hz / 120Hzの各レートで、押下位置と保持時間を組み合わせた10条件のうち8条件以上が成功する
- 発射だけ、または無関係なフリッパーでは得点と進行が変わらない
- 成功後に得点100、進行`1 / 5`、次目標、戻り表示、物理ゲートが一緒に変わる
- Chromium / WebKitで画面上の発射・フリッパー操作からHUD更新までを一本で確認する
- 320px / 390px / 430pxの縦画面で、盤面の下端が操作パネルに隠れず、盤面表示高470px以上を保つ

この10条件は決定論的な物理回帰であり、GAの人手による安全ショット成功率を代替しない。後続の物理シナリオでは、成功後の実球が`L0`は左、`R0`は右の対応フリッパーへ戻り、同側Pointer入力で実衝突することを60Hz / 120Hzで確認する。上向き再発射の操作感は別判定として残す。

初見理解、3〜5ゲーム後の上達、片側連打の支配性、iPhone Safariの表示・二本指・入力遅延・発熱・面白さは自動合格の対象にせず、管理端末の対面試遊で判定する。

## 4. GitHub Actionsのワークフロー

### 4.1 `ci.yml`

実行条件:

- pull request
- `main`へのpush
- 手動実行

既定権限:

```yaml
permissions:
  contents: read
```

CIはPagesへ公開しない。

### 4.2 品質ジョブ

G1-Aでは、次を一つの品質ジョブで連続実行する。

1. Node.jsとnpmの版確認
2. `npm ci`
3. 型検査
4. 静的検査
5. 単体試験
6. 物理読込試験
7. 本番形式ビルド
8. 容量確認
9. `dist`をArtifactへ保存

理由:

- `node_modules`を別ジョブへ渡さない
- lockファイルどおりの一回の取得で中心検査を行う
- 失敗箇所を一つのログで確認しやすい

実行時間が長すぎる場合は、複数ジョブへ分け、それぞれで`npm ci`する。npmキャッシュは使ってよいが、`node_modules`全体をArtifactで共有しない。

### 4.3 ブラウザジョブ

品質ジョブの`dist`をダウンロードする。

ブラウザ試験用コードのために`npm ci`を行い、ビルド済み`dist`を静的配信する。

Playwrightの初期必須:

- Chromium
- WebKit

Firefoxは追加負担が小さい場合だけ起動確認する。

### 4.4 `development-preview.yml`

用途:

- 信頼済みブランチをGitHub Pagesの確認枠へ出す

G1-Aの初回構築:

- 配置前に`github-pages` Environmentへユーザー本人の必須reviewerと、bootstrap push用`agent/g1a-technical-foundation`および手動更新・cleanup用`main`だけを許可するdeployment branch ruleを設定する
- 上記保護の確認後にだけRepository variable `DEVELOPMENT_PREVIEW_ENABLED=true`を設定する。未設定なら検査Artifactまででdeployをskipする
- 専用内部ブランチ`agent/g1a-technical-foundation`のpushだけを自動対象にする
- 同じワークフロー内で型、静的、単体、読込、ビルド、Chromium、WebKitを再確認してから配置する
- リポジトリ名とブランチ名をジョブ条件で再検査する

mainへワークフローを取り込んだ後:

- `workflow_dispatch`
- 入力: branchまたはcommit SHA、表示名
- 同一リポジトリ内の信頼済みrefだけを対象
- G1-A / G1-B、G3 / GAのマージ済み`agent/vertical-slice`、および理解性パス統合候補の`agent/ga-clarity-pages-sync`を明示allowlistし、checkoutしたSHAが対象ブランチの現在tipと一致する場合だけ実行
- `refs/pull/*`とallowlist外のSHAを拒否

外部フォークでは実行しない。

2026-08-12に公開URLを確認した結果、ルートが`/src/main.ts`を直接配信して「初期化中」のまま停止した。この状態はブラウザ試験の成功とは別のPages配信不備である。PagesのSourceをActionsへ設定し、検査済み`dist`を`/_preview/current/`へ配置してから、実URLの確認を行う。

### 4.5 `production-deploy.yml`

G7まで使用しない。

- `workflow_dispatch`
- GitHub Environment `production`
- ユーザー本人の承認
- 公開コミットSHAを入力

`main`への通常pushでは実行しない。

正式公開ジョブは開発、試験、ビルド、配置以外の処理を行わない。実行時API、定期集計、ランキング生成、配信網として使わない。

### 4.6 `preview-cleanup.yml`

G1-Aでは`workflow_dispatch`による手動実行で、Pages成果物から確認ページを外す。自動終了処理は、別の確認対象を誤って消す競合条件を設計してから再判断する。

終了後削除の確認は、G1-Aのpull requestをマージした後に記録する。一つのpull request内だけで終了後処理まで完了扱いにしない。

## 5. GitHub Pagesの確認枠

G1-Aで固定したG7前の構成:

```text
本番ルート:
<GitHub Pagesのプロジェクトルート>
  → 開発中の静的案内だけ

確認枠:
<プロジェクトルート>/_preview/current/
  → 現在確認中の信頼済みブランチ一件
```

実URLはREADMEや本書へ固定せず、ユーザー本人がActionsのdeployment summaryから開く。このURLは外部へ案内しない。ただし公開URLであり、推測アクセスを完全には防げない。

確認ページの実URL合格条件:

- ルートは`pages/root/root-guide.html`の案内だけを表示する
- `/_preview/current/`の`index.html`が`assets/*.js`を参照するビルド済み成果物である
- `src/main.ts`をブラウザへ直接配信しない
- ルートとプレビューの両方に`noindex`または`robots.txt`の検索除外がある
- 画面に環境名とビルドSHAが表示される
- `/_preview/current/`でWebGL起動、3球状態、結果、再挑戦、非保存境界を確認できる

### 5.1 一件だけにする理由

- 複数PR成果物の統合競合をなくす
- 別PRのファイルを削除する事故をなくす
- Pages成果物全体を毎回再構築できる
- 一人制作での管理負担を抑える

### 5.2 必須表示

確認ページへ次を表示する。

- `DEVELOPMENT PREVIEW`
- pull request番号または確認名
- コミットSHA
- ビルド日時
- 環境名
- 一般公開前であること

### 5.3 検索除外

- `robots.txt`
- `noindex,nofollow,noarchive`
- 本番ルートから確認枠へリンクしない
- OGPを設定しない

検索除外はアクセス制限ではない。

## 6. Actionsの安全性

- 既定`contents: read`
- Pagesジョブだけ`pages: write`と`id-token: write`
- 不要な`contents: write`を与えない
- 第三者Actionを完全なコミットSHAへ固定
- `pull_request_target`で未信頼コードを実行しない
- 外部フォークへ秘密情報を渡さない
- 外部フォークからのpull requestはCIだけ
- 公開ワークフロー変更は独立してレビュー
- Actionsを実行時API、サーバーレスアプリ、定期集計、配信網として使わない

同時実行:

```text
CI: ci-pr-<番号>
開発確認: pages-development-preview
正式公開: pages-production
```

開発確認と正式公開を同時に実行しない。

## 7. Vitestの範囲

### 7.1 入力

- pointerIdの所有と解除
- 短い`pressed`と`released`が同じ描画間隔に来ても消失しない
- 同じ物理ステップ前の押下・解放は、押下を一ステップ適用してから解放
- 入力イベントのsequenceId順
- 入力キュー上限超過で安全停止
- 不要な三本目の指で既存操作が変わらない
- `keydown`の`event.repeat`を新規押下にしない

### 7.2 状態

- `baseState`と`suspensionState`
- 発射待ち中の非表示から発射待ちへ戻る
- 球落下と非表示が同時でも球終了を失わない
- WebGL喪失中に得点が進まない
- 重大エラーが通常状態へ戻らない
- 許可されない遷移を拒否
- 再挑戦でRuleState、TableRuntimeState、ショット途中状態が初期化
- 再読み込みから進行中ゲームを復元しない

### 7.3 接触・得点

- SensorTransitionEvent
- ImpactEvent
- ContactOccupancy
- GameEvent
- ScoringEvent

を分ける。

- 同じscoringEventIdを二度処理しない
- beginとpostSolveを同じ意味として扱わない
- 接触コールバック内で物理世界を変更しない
- contact参照をステップ後まで保持しない

### 7.4 物理変更命令

- destroyとteleportの競合
- openとcloseの順序
- enableとdisableの順序
- 破棄済み対象への命令
- 256件上限
- 257件目で黙って捨てず安全停止

### 7.5 座標

- worldToScreenとscreenToWorldの往復
- 画面余白
- 回転方向
- 画面高さ変更
- 画面外タッチの拒否

### 7.6 非個人設定

- 環境別設定キー
- 一時キーから正式キーへの更新
- 読み戻し検査失敗
- 破損値から安全な初期値
- `development-preview`が通常処理で`production`設定キーを使わない
- 設定保存不能でもゲーム起動を妨げない
- 音、画面効果、高コントラスト、初回案内だけを許可
- 名前、ID、得点、履歴、回数、日時を含む設定は拒否

### 7.7 ゲーム記録の禁止

- `localStorage`へ得点、最高得点、履歴、回数を書かない
- `IndexedDB`へゲーム記録を書かない
- Cookieへゲーム記録を書かない
- アカウント、ログイン、名前登録の状態を持たない
- 外部分析、ランキング、認証、外部DB、決済のクライアントが存在しない

## 8. 物理シナリオ試験

### 8.1 再現可能性

乱数を使う場合はseedを固定する。

失敗時に次を出力する。

```text
seed
initialPosition
initialVelocity
physicsStepHz
fixtureIds
flipperState
failureStepId
```

### 8.2 試験行列

| 軸 | 条件 |
|---|---|
| 球速 | 通常、高速、上限直前 |
| 衝突角 | 正面、浅角、角 |
| 対象 | 外周、根元、先端、ゲート、狭路 |
| フリッパー | 休止、上昇、最大角、復帰 |
| 物理Hz | 60、120 |

単一の簡単な条件を10,000回繰り返しただけで合格としない。

### 8.3 必須シナリオ

- 高速球と外周
- フリッパー根元・先端
- 左右同時動作
- 発射強度3段階
- 安全ショットの正走、逆走、戻り
- 接触イベントの順序
- 物理変更命令の競合
- 正常な球受けを異常停止として回収しない
- 異常停止を安全位置へ戻す
- 同じ安全位置で再発した場合
- 60Hzと120Hzのゲーム時間
- 時間切り捨て後のrunIntegrity

`runIntegrity`は結果表示と診断にだけ使用し、保存や送信の判定には使わない。

## 9. Playwrightの範囲

### 9.1 表示

- デスクトップ
- 幅320px
- 幅390px前後
- 幅430px
- 縦画面
- 横画面案内
- Safari相当の可変表示高さを模したresize

### 9.2 操作

- タイトルから開始
- 発射
- 左右フリッパー個別
- キーボード
- ポーズ・再開
- 結果・エラー画面
- 画面サイズ変更
- 非表示・復帰の模擬

- 再挑戦による状態初期化
- 再読み込みで進行中ゲームを復元しないこと

Playwrightでは実際の二本指同時入力を完全再現できないため、GA開始時の端末確認へ残す。

### 9.3 ループ

- 稼働中GameLoopが一件
- PixiJS自動Tickerが無効
- HMR相当の再初期化後も一件
- 連続ゲーム開始で描画回数が倍増しない

### 9.4 アクセシビリティ

- キーボードだけで開始、発射、左右、ポーズ、終了
- メニューと結果の主要操作へ移動
- 主要操作対象が最低24×24 CSSピクセル
- 主ボタンは可能な範囲で44×44 CSSピクセル前後
- `prefers-reduced-motion`を初期設定へ反映
- 一秒に3回を超える強い点滅を作らない

### 9.5 ネットワーク

- 同一オリジンの静的素材以外の自動要求0件
- 認証、ランキング、外部DB、外部分析、広告、決済の要求0件
- ゲーム開始、終了、得点を送る要求0件
- 共有APIの呼び出しを外部自動送信と混同しない

### 9.6 失敗時成果物

- スクリーンショット
- trace
- コンソールログ
- 未処理例外
- ブラウザと表示サイズ
- コミットSHA

成功時はtraceや動画を常時保存しない。

## 10. iPhone・iPadをまとめて確認する節目

各実装PRでは端末確認を要求しない。次の二回を標準とする。

1. GA開始時: G1-Aの表示・保存とG1-Bの入力・物理を一度に確認する
2. RC: 公開候補コミットで対応端末とSafariの最終確認を行う

端末固有のP0またはP1が疑われる場合だけ、この二回以外でも対象を絞って確認する。

### 10.1 GA開始時に引き継ぐG1-A項目

- GitHub Pages確認枠をSafariで開く
- 確認ページの環境名とコミットSHA
- 本番ルートにゲームが出ていない
- rootと確認ページがnoindex
- 確認版の設定が本番設定キーを通常使用しない
- 設定保存を無効にしても起動・停止できる
- 画面高さ変化で見切れない

### 10.2 GA開始時に引き継ぐG1-B項目

- 左右二本指同時
- 左右を押したまま不要な三本目
- 指を別領域、画面外へ移動
- 非常に短いタップ
- 通知センター、アプリ切り替え、画面ロック
- 縦横切り替え
- 発射操作2案

```text

```

- その画面の物理ステップ数
