## 1. この文書の役割

本書は、どの不具合をどの試験で検出するかと、マージ前にiPhoneで確認する方法の正本である。

自動試験だけで実機品質を保証しない。一方で、実機確認だけに頼り、毎回同じ不具合を手作業で探す状態にも戻さない。

---

## 2. 試験の層

| 層 | 主な道具 | 確認対象 |
|---|---|---|
| 型・静的検査 | TypeScript、ESLint相当 | 型、未使用、危険な依存方向 |
| 単体試験 | Vitest | 得点、状態遷移、入力所有、盤面検査 |
| 物理シナリオ試験 | Vitest + Planck.js | 壁抜け、保持候補、接触重複、再配置 |
| ブラウザ自動試験 | Playwright Test | 起動、画面、キーボード、Pointer Events、WebGL |
| 実機確認 | iPhone、iPad | 二本指、Safari、音声、発熱、体感遅延 |
| 試遊 | 限定URLと試遊手順 | 理解、上達、公平感、中心体験 |

PlaywrightのWebKitはSafariそのものではない。WebKit系の早期不具合検出には使うが、iPhone Safari試験の代わりにはしない。

## 3. GitHub Actionsの構成

### 3.1 pull_request時

必須ジョブ:

1. `install`
   - Node.jsの正確な版を使用
   - `npm ci`
   - lockファイル不整合で失敗
2. `typecheck`
3. `lint`
4. `unit-test`
5. `physics-test`
6. `build`
7. `bundle-budget`
8. `e2e-chromium`
9. `e2e-webkit`
10. `preview-deploy`

`preview-deploy`は、型検査・単体試験・ビルドが成功した場合だけ実行する。

### 3.2 main取り込み時

- pull request時の検査を再実行
- 本番ビルド
- GitHub Pages本番へ公開
- 公開URLの起動確認
- 直前の本番版をロールバック候補として記録

### 3.3 PR終了時

- PRプレビューのディレクトリを削除
- 削除失敗を運用課題として記録
- 本番ディレクトリへ影響を与えない

### 3.4 同時実行

同じPRでは古い実行をキャンセルする。

```text
concurrency group: preview-pr-${PR_NUMBER}
cancel-in-progress: true
```

本番公開は別の同時実行グループを使い、PRプレビューと競合させない。

## 4. PRプレビュー

### 4.1 採用方針

G1ではGitHub Pages配下のPR別URLを第一候補とする。

```text
本番:
https://chameleonjp-lab.github.io/doppan/

PRプレビュー:
https://chameleonjp-lab.github.io/doppan/previews/pr-<番号>/
```

プレビューURLは、マージ前にiPhoneから開くために使う。

### 4.2 分離規則

- PR番号ごとに別ディレクトリ
- `base`パスをPR用に設定してビルド
- 本番の`index.html`や素材を上書きしない
- PRクローズ後に該当ディレクトリだけ削除
- プレビューへ本番用の秘密情報を入れない
- Supabaseなどの外部接続はG1では使用しない
- `robots`相当で検索結果への掲載を抑える
- 画面上にPR番号とコミットSHAを表示できる

### 4.3 実装方式

専用のPages公開ブランチまたは公開用成果物へ、次の構成でまとめる。

```text
/
├─ index.html                 # 本番
├─ assets/                    # 本番
└─ previews/
   ├─ pr-4/
   ├─ pr-5/
   └─ ...
```

PRプレビュー公開では、既存の本番と他PRの成果物を保持したうえで、対象PRのディレクトリだけを更新する。

標準のPagesデプロイがサイト全体を置き換える構成になった場合は、次の代替へ切り替える。

- Cloudflare PagesなどのPRプレビュー機能
- 別のプレビュー専用リポジトリ

本番をPRビルドで上書きする方式は採用しない。

### 4.4 プレビュー合格条件

- PR本文またはActions SummaryからURLを開ける
- iPhone SafariでHTTPS表示できる
- PR番号とコミットSHAを確認できる
- 本番URLが変化しない
- PR更新で同じURLが更新される
- PR終了後に削除される

## 5. Vitestの範囲

### 5.1 単体試験

- GameStateMachineの許可・禁止遷移
- 同一物理ステップの遷移優先順位
- pointerIdの所有・解除
- `keydown`自動連打の無視
- 得点イベントの一回処理
- 球間で残す進行と解除する状態
- ボールセーブ
- 保存データ移行
- 不正な盤面データ拒否
- ショット状態機械
- 診断履歴の上限

### 5.2 物理シナリオ試験

- 高速球と外周壁
- フリッパー先端衝突
- 左右フリッパー同時動作
- 発射強度3段階
- 安全ショット通過
- 接触コールバック内で物理世界を変更しない
- 接触バッファの重複除去
- 物理変更予約の実行順
- 正常な球受けを異常停止として回収しない
- 異常停止を安全位置へ戻す
- 同じ安全位置での再発防止
- ゲーム再開始20回後のbody・fixture・joint数

浮動小数点の完全一致だけを要求しない。

比較するもの:

- 許容範囲内の位置・速度
- 接触とショットイベントの順序
- 得点イベント数
- 盤面外逸脱
- 非有限値

## 6. Playwrightの範囲

### 6.1 実行ブラウザ

G1では次を必須とする。

- Chromium
- WebKit

Firefoxは正式版1.0の必須対象ではないが、追加負担が小さい場合は起動確認を行う。

### 6.2 画面構成

- デスクトップ
- 幅320px
- 幅390px前後
- 幅430px
- 縦画面
- 横画面案内

### 6.3 自動操作

- タイトルから技術試作を開始
- 発射
- 左右フリッパーの個別入力
- キーボード操作
- ポーズと再開
- 結果・エラー案内の主要ボタン
- 画面サイズ変更
- `visibilitychange`相当の停止・復帰
- WebGL初期化失敗時の案内
- 共有APIとクリップボードがない場合の代替

Playwrightのタッチ操作は実機の複数指入力を完全には再現しない。二本指同時操作はiPhone実機の必須確認に残す。

### 6.4 失敗時成果物

- スクリーンショット
- Playwright trace
- コンソールログ
- 未処理例外
- 対象ブラウザと表示サイズ

成功時は動画やtraceを常時保存せず、保存量を抑える。

## 7. キーボード入力試験

初期割り当て:

```text
左フリッパー: Z / ArrowLeft
右フリッパー: / / ArrowRight
発射: Space
ポーズ: Escape
```

規則:

- `event.repeat`による連打を新しい押下として処理しない
- `keyup`で解除
- `blur`と`visibilitychange`で全解除
- テキスト入力欄やボタン操作中はゲームキーを横取りしない
- タイトル、発射、左右、ポーズ、結果、終了をキーボードだけで操作できる

## 8. 入力遅延の記録

内部処理と画面反映を分けて測る。

```text
pointerEventTime
physicsAppliedTime
renderScheduledTime
renderedFrameTime
```

記録値:

- 入力から物理反映まで
- 入力から次の描画まで
- 物理ステップ待ち時間
- その画面で実行した物理ステップ数

実際の液晶表示完了時刻まではブラウザから取得できないため、最後は実機の体感確認も行う。

## 9. iPhone・iPad実機確認

### 9.1 G1必須

- PRプレビューURLをSafariで開く
- 左右二本指を同時に押す
- 左右を押したまま不要な三本目を追加
- 指を別領域へ移動
- 指を画面外へ移動
- 通知センターやアプリ切り替え後に戻る
- 画面をロックして戻る
- 縦横を切り替える
- 発射操作2案を比較
- 音声がある段階では初回開始と復帰を確認

### 9.2 記録

- 端末
- OS
- Safari版
- PR番号
- コミットSHA
- 操作結果
- 入力押しっぱなし
- 体感遅延
- 発熱
- 画面見切れ

### 9.3 自動試験との関係

Playwrightで成功していても、次は実機で不合格になり得る。

- 二本指入力
- Safariの音声制限
- WebGL復帰
- ホームインジケータ周辺
- 120Hz画面の体感
- 発熱と電池消費

実機不合格を自動試験成功で上書きしない。

## 10. WebGL喪失と復旧

合格は二経路のどちらかとする。

### A. 自動復旧

1. `webglcontextlost`を受け取る
2. 既定動作を止める
3. 入力・物理・得点を停止
4. 論理状態を保持
5. `webglcontextrestored`後にGPU資源を再構築
6. 手動再開待ちを表示
7. ユーザー操作で再開

### B. 安全停止

自動復旧できない場合:

- 白画面にしない
- 入力を全解除
- 物理と得点を進めない
- 再読み込み案内を表示
- 進行中ゲームは復元しない方針を明示

RCで「常に自動復旧」だけを合格条件にしない。安全停止経路でも、操作不能や白画面を残さなければ技術的に合格可能とする。

## 11. 資源増加の試験

20回のゲーム再開始と30分連続試験で確認する。

- body、fixture、joint数が基準へ戻る
- PixiJS表示オブジェクトが増え続けない
- イベント購読数が増えない
- 同時再生音が終了後0へ戻る
- 接触バッファが各物理ステップ後に空になる
- 物理変更予約が残らない
- 診断履歴と試遊レポートが上限以内

ブラウザのメモリ値が取得できない場合も、内部個数の不整合は不合格とする。
