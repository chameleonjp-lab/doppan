## 1. この計画書の目的

DOPPANを、iPhoneのブラウザで快適に遊べる2Dピンボールとして実装し、技術品質とゲーム品質の両方を満たすための工程を定める。

本計画では、単に機能を完成させるだけでは通過としない。

- 球が正しく動く
- タッチが確実に反応する
- 狙い分けが成立する
- 得点と進行が理解できる
- 見た目と音が操作を助ける
- 初見プレイヤーが遊び方を理解する
- DOPPAN固有の価値を説明できる

この全てを段階的に確認する。

## 1.1 文書の優先順位

判断が衝突した場合は、次の順で扱う。

1. 安全、権利、プレイヤーの公平性
2. ゲーム制作・プロデュース計画書の作品方針
3. 本書の品質条件
4. 個別の実装方法
5. 作業量を減らす都合

実装済みであっても、作品方針と面白さ条件を満たさない場合は作り直す。

## 2. 採用する基本方針

## 2.1 ゲーム形式

- 2Dのベクター調表現
- 縦画面、固定カメラ、1盤面
- 1人用スコアアタック
- 1ゲーム3球
- iPhone Safariを最優先
- iPadとPCブラウザにも対応
- MVPではオンライン接続を必須にしない
- 物理、描画、ルール、画面を分離する

## 2.2 遊びの中心

実装は次の体験を支える。

- フリッパーの位置とタイミングで球筋が変わる
- 球を短時間保持し、狙って打てる
- 安全、中核、危険ショットを選べる
- 成功後の戻り位置から次の判断が生まれる
- 盤面目標の達成によって得点効率が変わる
- 失敗理由を位置と入力から理解できる

## 2.3 MVPに含めないもの

以下は、MVPの技術条件と面白さ条件が通過した後に検討する。

- 完全3D表示
- 複数盤面
- オンラインランキング
- アカウント登録
- 対人戦
- マルチボール
- 台を揺らす操作
- ユーザー作成盤面
- 課金、広告、ガチャ
- 大規模な物語
- 多数のモード

## 3. 技術選定

## 3.1 言語: TypeScript

ゲームの中心処理をTypeScriptで統一する。

型で区別する主なもの:

- ゲーム状態
- 盤面部品ID
- ショットID
- 接触イベント
- 得点イベント
- モード状態
- 入力状態
- 保存データ版
- 盤面版
- ルール版

`any`を中心処理の逃げ道として使わない。不明な外部入力は`unknown`として受け、検査後に使用する。

## 3.2 描画: PixiJS

PixiJSは次を担当する。

- 盤面背景
- 球
- フリッパー
- ライト
- 得点表示
- 目標表示
- 粒子
- 球の軌跡
- 画面演出

物理判定の形と見た目を分ける。表示画像の変更が物理挙動へ影響しない構成にする。

## 3.3 物理計算: Planck.js

Planck.jsで次を管理する。

- 球
- 外周壁
- レール
- フリッパー
- 発射装置
- バンパー
- スリングショット
- ゲート
- 見えないセンサー
- 落下判定

球は高速物体として扱い、連続衝突判定を利用する。

## 3.4 開発と配信: Vite

ViteでTypeScript、画像、音声、設定ファイルをブラウザ配信用にまとめる。

GitHub Pages配下で動作するよう、公開先の基底パスを設定する。

## 3.5 自動テスト: Vitest

次を主に自動化する。

- ゲーム状態
- 得点ルール
- 盤面データ検査
- 保存データ移行
- 物理試験
- 入力状態解除
- イベント重複防止

## 3.6 公開: GitHub ActionsとGitHub Pages

`main`への取り込み後、GitHub Actionsで次を実行する。

1. 依存関係をlockファイルどおりに取得
2. 型検査
3. 静的検査
4. 自動テスト
5. 本番ビルド
6. 配信物の容量確認
7. GitHub Pagesへ公開

Node.jsの版は固定する。初期案はNode.js 24とし、採用ライブラリとGitHub Actionsの実行結果を確認して確定する。

## 4. システム構成

## 4.1 全体構成

```text
入力
 ↓
ゲーム進行管理
 ↓
物理操作命令 ─────→ 物理計算
                         ↓
盤面ルール ← 接触・通過イベント
    ↓                    ↓
得点・モード          位置・速度
    ↓                    ↓
表示指示・音指示 ← 描画同期
    ↓
画面・音・触覚
```

物理処理は、得点や演出を直接決めない。

盤面ルールは、表示ライブラリへ直接命令しない。意味のあるゲームイベントを発行し、描画と音が受け取る。

## 4.2 推奨ディレクトリ構成

```text
/
├─ docs/
│  ├─ GAME_PRODUCTION_PLAN.md
│  ├─ IMPLEMENTATION_PLAN.md
│  └─ EXPANSION_IDEAS.md
├─ public/
│  └─ assets/
│     ├─ images/
│     ├─ audio/
│     └─ fonts/
├─ src/
│  ├─ app/            # 起動、画面遷移、全体設定
│  ├─ game/           # ゲーム進行、残り球数、ポーズ
│  ├─ physics/        # Planck.js接続、固定時間、物理同期
│  ├─ table/          # 盤面データ、部品生成、ショット定義
│  ├─ rules/          # 得点、倍率、進行、モード
│  ├─ rendering/      # PixiJS描画、ライト、粒子、軌跡
│  ├─ input/          # タッチ、キーボード、入力解除
│  ├─ audio/          # 効果音、音量、再生優先度
│  ├─ haptics/        # 利用可能な端末での短い触覚
│  ├─ storage/        # 設定、最高得点、保存データ移行
│  ├─ telemetry/      # 開発用の匿名集計、イベント記録
│  ├─ debug/          # 判定表示、履歴、性能表示
│  └─ ui/             # タイトル、ポーズ、結果、設定
├─ tests/
│  ├─ unit/
│  ├─ physics/
│  └─ fixtures/
└─ .github/workflows/
```

初期段階で空ファイルを大量に作らない。責任の分離が必要になった時点で分割する。

## 4.3 依存方向

次の方向を守る。

```text
UI・描画・音
    ↓
ゲーム状態とイベント
    ↓
盤面ルール
    ↓
物理接続
```

逆方向の参照を避ける。

例:

- 物理処理からPixiJSを呼ばない
- 得点ルールからHTML要素を触らない
- 音声ファイル名を盤面ルールへ直接書かない
- UIからPlanck.jsの物体を直接動かさない

## 5. 座標、時間、数値の基準

## 5.1 盤面座標

盤面座標は画面のピクセル数ではなく、ゲーム内の共通単位で管理する。

表示時だけ画面サイズへ変換する。

これにより、端末サイズが変わっても次を維持する。

- 球の速度
- 重力
- フリッパーの長さ
- 壁の厚さ
- 得点判定位置

## 5.2 固定時間刻み

物理計算は描画速度と分け、一定間隔で進める。

初期比較:

- 1秒60回
- 1秒120回

比較項目:

- 球のすり抜け
- フリッパーの反応
- 保持の安定性
- バンパー接触
- iPhoneでの負荷
- 画面復帰時の挙動

1描画内で進める物理回数に上限を設ける。長時間非表示だった後に、停止中の時間をまとめて進めない。

## 5.3 数値設定の集中管理

次を一か所または明確な設定単位へ集める。

- 重力
- 球の半径と質量
- 反発
- 摩擦
- 球速上限
- フリッパー角度
- フリッパー速度
- 発射力
- ボールセーブ時間
- 接触再得点待ち時間
- 各得点

変更理由を記録し、無根拠な微調整を積み重ねない。

## 6. 盤面データ

## 6.1 盤面定義

盤面の形、部品、ショット、得点値をゲーム処理から切り離したデータで定義する。

初期の定義対象:

- 盤面サイズ
- 外周壁とレール
- 球の開始位置
- 左右フリッパー
- 発射レーン
- バンパー
- スリングショット
- 通過レーン
- 目標
- アウトレーン
- 中央落下口
- 見えないセンサー
- ショット入口と出口
- 部品ID
- ショットID
- 得点と進行価値

## 6.2 盤面データ検査

読み込み時に次を拒否する。

- ID重複
- 必須座標不足
- 負または0の大きさ
- 対応していない部品種別
- 盤面外の重要部品
- 存在しない参照先
- 同じショットIDの重複
- 落下口がない
- 球の初期位置が部品内部にある
- フリッパーの回転範囲が不正

## 6.3 ショット定義

ショットは見えないセンサー一個だけで判定しない。

必要に応じて次を組み合わせる。

- 入口通過
- 方向
- 出口通過
- 通過順序
- 最低速度
- 同一球内の重複防止

一度戻っただけの球を、成功ショットとして誤判定しない。

## 6.4 盤面版とルール版

次を別に持つ。

- `tableVersion`: 形状、部品位置、物理値が変わった版
- `rulesVersion`: 得点、進行、モード条件が変わった版
- `clientVersion`: アプリ全体の版

公開後の記録や不具合報告に含める。

## 7. 物理実装

## 7.1 球

球は次を持つ。

- 一意なID
- 現在位置
- 速度
- 回転
- 所属状態
- 最後に安全だった位置
- 最後に動いた時間
- 発射または再配置の理由

MVPは1球のみとするが、将来の複数球でIDを追加できる構成にする。

## 7.2 フリッパー

フリッパーは回転関節として実装し、次を設定できるようにする。

- 休止角度
- 最大角度
- 上昇速度
- 復帰速度
- 最大トルク
- 入力中か
- 左右区分

品質条件:

- 根元と先端で球筋が変わる
- 押し続けると球を保持できる
- 離すと確実に戻る
- 左右同時入力ができる
- 連打しても角度が壊れない
- 球が内部へ潜り込まない

## 7.3 フリッパー上の保持判定

停止球検出とは別に、正常な保持状態を判定する。

保持中と見なす条件の例:

- 球がフリッパー近辺にある
- フリッパーが上がっている
- 球速が低い
- 球が盤面内にある
- 一定範囲内で接触が続いている

正常な保持中は自動回収しない。

## 7.4 バンパーとスリングショット

物理的な反発とゲーム上の接触イベントを分ける。

同じ接触が複数の物理ステップで続いても、意図しない二重得点を出さない。

反発力は、球速を無制限に増やさない。

## 7.5 発射装置

MVPでは次のどちらかを比較する。

- 発射領域を引いて離す
- 発射ボタンを押し続けて離す

確認内容:

- 指で盤面を隠しすぎない
- 発射強度を再現できる
- 最大と最小の差が理解できる
- 誤ってフリッパーを動かさない
- スキルショットへ使える精度がある

## 7.6 安全な再配置

球が異常状態になった場合、次の順で対応する。

1. 異常判定を記録
2. 正常な保持ではないことを確認
3. 最後に安全だった位置を確認
4. 速度を制限して再配置
5. 同じ異常が繰り返す場合は球終了

プレイヤーに不利な回収を行った場合は、残り球を減らさないことを基本とする。

## 8. ゲーム状態

最低限、次の状態を明確に分ける。

- 起動中
- タイトル
- 初回案内
- 発射待ち
- プレイ中
- ボールセーブ再発射
- ボール終了処理
- 次球準備
- 一時停止
- ゲーム終了
- 結果表示
- 練習中

状態ごとに許可する処理を定義する。

例:

- 一時停止中は物理計算と得点を止める
- 結果画面では接触イベントを受け取らない
- 次球開始時に全入力を解除する
- 発射待ち中は盤面得点を進めない
- 練習中はランキング対象にしない

状態遷移はイベントとして記録し、直近の履歴を確認モードで表示できるようにする。

## 9. 接触イベントと盤面ルール

## 9.1 イベント例

物理処理は部品IDと球IDを使って次を通知する。

- バンパー接触
- スリングショット接触
- レーン入口通過
- レーン出口通過
- 目標接触
- 発射レーン離脱
- アウトレーン進入
- 中央落下
- 球の異常停止
- 球の正常保持開始
- 球の正常保持終了

## 9.2 イベント共通情報

各イベントは必要に応じて次を持つ。

- イベントID
- 物理時刻
- 球ID
- 部品ID
- ショットID
- 接触位置
- 接触速度
- 進入方向
- 盤面版
- ルール版

## 9.3 得点処理

盤面ルールがイベントを受け、次を決める。

- 基本得点
- 倍率
- コンボ
- 進行
- ライト
- ボーナス開始
- ボーナス終了
- 結果表示用内訳

一つのイベントに対する得点処理を一度だけ行う。

## 9.4 得点内訳

MVPから、結果画面へ出せる形で分類して保存する。

- バンパー
- スリングショット
- 安全ショット
- 中核ショット
- 危険ショット
- レーン完成
- 目標完成
- ボーナス
- コンボ
- その他

数値調整と支配的攻略の検出に使う。

## 10. 入力

## 10.1 共通入力状態

タッチとキーボードを共通の操作へ変換する。

- 左フリッパー押下
- 左フリッパー解放
- 右フリッパー押下
- 右フリッパー解放
- 発射開始
- 発射強度変更
- 発射
- ポーズ
- 再開

## 10.2 タッチ操作

MVPの基本:

- 画面左側の操作領域: 左フリッパー
- 画面右側の操作領域: 右フリッパー
- 発射専用領域: 発射装置
- 上部の独立ボタン: ポーズ

必須対策:

- 左右を同時に押せる
- 複数の指を個別に追跡する
- 指が領域外へ移動した時に解除する
- `pointercancel`を処理する
- 画面非表示時に全入力を解除する
- アプリ切り替え後に押しっぱなしを残さない
- ページスクロールと拡大操作を抑止する
- ポーズとフリッパーが同時発動しない
- 押した状態を指の外側から確認できる

## 10.3 タッチ領域

主要操作は十分な広さを持たせる。

画面の下部だけを小さいボタンで区切るのではなく、盤面を隠さない範囲で左右に広い入力領域を用意する。

安全領域、ホームインジケータ、Dynamic Islandなどと重ならないようにする。

## 10.4 キーボード

初期割り当て候補:

- 左: `Z`、左矢印
- 右: `/`、右矢印
- 発射: Space
- ポーズ: Escape

開始、設定、プレイ、結果、終了までキーボードだけでも操作できるようにする。

## 11. 表示

## 11.1 画面構成

- 上部: 得点、倍率、残り球、現在目標
- 中央: 盤面
- 下部: 操作領域と安全領域

端末の縦横比によって、盤面の物理座標を変えず、余白とUI配置を調整する。

## 11.2 球の視認性

MVP必須:

- 背景と十分な差がある
- 輪郭またはハイライトがある
- 高速時の短い軌跡を設定できる
- 強い発光中も球を見失わない
- 球の軌跡は物理判定に影響しない

## 11.3 目標表示

次に狙う場所を、色だけに頼らず示す。

候補:

- 外周形状
- 模様
- 短い文字
- 矢印
- 明るさ
- 点灯順序

常時全てを点滅させない。

## 11.4 演出優先度

1. 入力したことが分かる
2. 接触したことが分かる
3. 得点の価値が分かる
4. 次の目標が分かる
5. 重要な達成に特別感がある

演出で球、フリッパー、目標を隠さない。

## 12. 音と触覚

## 12.1 効果音

MVP候補:

- フリッパー作動
- 発射
- 壁接触
- バンパー接触
- スリングショット
- ショット成功
- 目標完成
- ボーナス開始
- ボール終了
- ゲーム終了

## 12.2 音の優先度

短時間に多くの接触が起きても、全てを最大音量で重ねない。

- 重要音を優先する
- 同じ音の同時再生数を制限する
- 接触速度で音量と高さを小さく変える
- 音なしでも同じ情報を画面で得られる

## 12.3 初期設定

効果音はユーザー操作後に有効化する。

設定:

- 音なし
- 効果音音量
- 音楽音量

音の初期値は、公開前に実機試遊で決定する。

## 12.4 触覚

MVP必須にはしない。

導入する場合:

- フリッパー入力
- 強い衝突
- 重要なモード開始

など、原因が明確な短い場面へ限定する。

無効化でき、触覚なしでも情報が欠けないようにする。

## 13. 保存

MVPではブラウザ内へ次を保存する。

- 最高得点
- 得点内訳の自己最高
- 効果音設定
- 音楽設定
- 画面効果設定
- 球の軌跡設定
- 初回説明を確認したか
- 保存データ版

保存に失敗してもプレイを続けられるようにする。

保存データは版を持ち、将来の変更で読み込めない場合に安全な初期値へ移行する。

## 14. 開発用確認機能

通常プレイヤーには表示しない確認モードを用意する。

- 物理判定形状
- 球の位置、速度、回転

## 15. MVPのゲーム仕様

## 15.1 基本ルール

- 1ゲーム3球
- 中央またはアウトレーンから落ちると1球終了
- 各球の開始直後に短いボールセーブ
- ボールセーブ中の落下では残り球を減らさない
- 3球終了後に結果画面
- 再挑戦と終了を同じ強さで表示

## 15.2 盤面部品の初期上限

部品数は先に固定せず、ショットマップから必要数を決める。

初期上限の目安:

- 左右フリッパー: 2本
- 発射装置: 1基
- バンパー: 2〜3個
- スリングショット: 左右1個ずつ
- 通過レーン: 2〜3本
- 明確な狙いショット: 左右合計3〜5本
- 目標: 2〜4個
- アウトレーン: 左右1本ずつ
- 中央落下口: 1か所

部品数ではなく、意味のあるショット数を優先する。

## 15.3 ショット構成

MVPは最低限、次を持つ。

- 安全ショット
- 中核ショット
- 危険ショット
- 反対側フリッパーへつながるショット
- 盤面進行を完成させるショット

左右フリッパーから狙える場所と成功後の戻りを文書化してから配置する。

## 15.4 得点と倍率

初期値はプロデュース計画書の比率を基準に仮設定し、試遊で調整する。

- 壁接触: 原則得点なし
- 偶発的な接触: 小得点
- 安全ショット: 小〜中得点
- 中核ショット: 中得点と進行
- 危険ショット: 高得点またはモード進行
- 目標完成: ボーナスまたは倍率

## 15.5 MVPのボーナスモード

一つの進行条件を完成すると、短時間だけ得点効率が上がる。

現在の仮案:

- 指定ショットと目標を完成
- 一定時間2倍
- 進行を初期化

テーマ決定後、単なる「2倍」ではなく、世界観と固有動詞に沿った名称と目標へ変更する。

必要表示:

- 未達成箇所
- 完成時の短い演出
- 残り時間
- 倍率が適用された得点
- 終了理由

## 19. 性能方針

## 19.1 優先順位

負荷が高い場合は次の順で削減する。

1. 不要な粒子
2. 影
3. 発光解像度
4. 軌跡点数
5. UI更新頻度
6. 画像解像度

物理計算回数を最初に減らさない。

## 19.2 実装上の注意

- 毎描画で不要な配列を作らない
- DOMを毎描画で大量更新しない
- 使い終わった表示物を破棄する
- 音声ノードを残し続けない
- イベント購読を解除する
- ゲームループを二重起動しない
- 画像と音を開始前に全て読み込まない

## 19.3 配信物

公開前に次を記録する。

- JavaScript総容量
- 初回画像容量
- 初回音声容量
- 初回表示までの時間
- 追加読み込み失敗時の動作

厳密な容量上限は縦切り完成時に、実機計測を基に決定する。

同じ意味の音を将来差し替えられるようにする。

## 21. 責任ある継続設計

ゲームの継続は、選択、技能、発見、自己改善から作る。

採用する:

- 自分の判断で再挑戦できる
- 得点内訳を確認できる
- 失敗理由を確認できる
- 1ゲームに明確な終了がある
- 終了後に自動保存する
- 演出の強さを選べる

採用しない:

- 有料ランダム
- 期限付き主要報酬
- ログインしないと失う進捗
- 外れを過大に惜しく見せる演出
- 結果と無関係な疑似操作
- 小得点を大勝利として祝う表示
- 終了を見つけにくくする画面
- 再挑戦だけを目立たせる結果画面
- 深夜や連敗を狙った呼び戻し

品質指標には、プレイ時間だけでなく終了後満足度、公平感、理解度、自主的な再挑戦理由を含める。

## 24. MVP完成条件

次を全て満たした時点でMVP完成とする。

## 24.1 物理

- 成功後に次の判断がある
- 一つの行動だけが最高効率にならない
- 得点が狙った行動を中心に評価する
- グレー盤面の初見試遊を通過する

## 24.4 ルール

- 3球、得点、進行、倍率、ボーナス、終了が一貫して動く
- 一度の接触で二重得点しない
- ポーズ中と結果画面で得点が進まない
- 再開始時に前回状態が残らない
- 得点内訳を表示できる

## 24.5 初回体験

- 長い説明なしで開始できる
- 最初の1ゲームで基本操作を理解できる
- 次に狙う場所が分かる
- 残り球と失敗理由が分かる
- 終了と再挑戦を迷わず選べる

## 24.6 表示と性能

- 対象端末で盤面が見切れない
- 球を見失いにくい
- 通常プレイで継続的な大きな処理落ちなし
- 15分連続で操作遅延が悪化しない
- 不要な球、演出、音が残らない

## 24.7 公開品質

- 型検査成功
- 自動テスト成功
- 本番ビルド成功
- GitHub Pages公開成功
- 未処理エラーなし
- 素材と外部ライブラリの出所記録
- 既存作品の画像、音、盤面、ROM、商標を無断使用していない
