- 文書種別: 実装方針・開発計画
- 作成日: 2026-08-09
- 対象リポジトリ: `chameleonjp-lab/doppan`
- 状態: 方針確認済み・実装開始前
- 関連文書: [今後の拡張アイデア](./EXPANSION_IDEAS.md)

## 1. この計画書の目的

DOPPANを、iPhoneのブラウザで快適に遊べる2Dピンボールゲームとして完成させるための実装方針を定める。

最初から機能を増やしすぎず、まず「球を打つ、狙う、得点する、3球を遊び切る」というピンボールの中心部分を安定させる。その後、演出、ミッション、ランキングなどを段階的に追加する。

この文書は実装順序と完成条件を固定するためのものとし、個別の数値調整やテーマ表現は、実機確認を通じて更新する。

## 2. 採用する基本方針

### 2.1 ゲーム形式

- 2Dのベクター調表現
- 縦画面、固定カメラ、1盤面
- 1人用のスコアアタック
- 1ゲーム3球
- iPhone Safariを最優先
- iPadとPCブラウザにも対応
- MVPではオンライン接続を必須にしない

### 2.2 遊びの中心

プレイヤーが上達を実感できることを優先する。

- フリッパーの打つ位置とタイミングで球筋が変わる
- 狙う場所を選ぶ意味がある
- 盤面上の目標を順に達成すると得点効率が上がる
- 偶然だけでなく、操作と判断が結果へ反映される
- 1プレイの失敗理由を理解できる

派手な演出は補助として使い、得点や当たりを誤認させる表示は使わない。

### 2.3 MVPに含めないもの

以下は基礎部分が安定した後に検討する。

- 3D表示
- 複数盤面
- オンラインランキング
- アカウント登録
- 対人戦
- マルチボール
- 盤面を揺らす操作
- ユーザー作成盤面
- 課金、広告、ガチャ
- 大規模な物語や多数のミッション

## 3. 技術選定

## 3.1 言語: TypeScript

通常のJavaScriptへ型の検査を加え、得点、残り球数、盤面部品、イベントなどの受け渡しミスを実行前に見つけやすくする。

AIによる継続的な修正では、変更範囲が広がったときに型検査が安全網になる。ゲームの中心処理はTypeScriptで統一する。

## 3.2 描画: PixiJS

PixiJSは、盤面背景、球、フリッパー、ライト、文字、粒子、画面演出を描画するために使う。

物理判定と見た目を分け、判定用の壁を少し厚くしながら、画面上では細いレールとして表示できる構成にする。

採用理由:

- 2D描画に集中した構成
- CanvasとWebGLを扱える
- iPhoneを含むブラウザ向け実績が多い
- MITライセンス
- 物理処理を別の仕組みに分離しやすい

## 3.3 物理計算: Planck.js

Planck.jsで、球、壁、フリッパー、バンパー、発射装置、スリングショット、落下判定を管理する。

高速で動く球が壁を通り抜けないよう、球を高速物体として設定し、連続衝突判定を利用する。

採用理由:

- Box2D系の安定した2D物理処理
- 高速物体向けの衝突対策を持つ
- 回転するフリッパーを接続部品として扱える
- TypeScriptから使用できる
- MITライセンス

## 3.4 開発と配信: Vite

TypeScript、画像、音声、設定ファイルをブラウザ配信用にまとめる。

手元のiPhoneでビルドすることを前提にせず、GitHub Actions上で検査と公開を行う。

## 3.5 自動テスト: Vitest

得点ルール、ゲーム状態、ボールセーブ、倍率、ゲーム終了などを自動で確認する。

物理挙動については、同じ初期条件で球を発射し、盤面外へのすり抜け、停止、異常速度が発生しないかを確認する試験を追加する。

## 3.6 公開: GitHub Pages

`main`への取り込み後、GitHub Actionsで次を実行する。

1. 依存関係を固定して取得
2. 型検査
3. 自動テスト
4. 本番ビルド
5. GitHub Pagesへ公開

Node.jsは、採用ライブラリとの互換性を確認したうえで、GitHub Actions内のバージョンを固定する。初期案はNode.js 24とする。

## 4. システム構成

## 4.1 全体構成

ゲームを次の役割へ分ける。

```text
画面・入力
  ↓
ゲーム進行管理
  ↓
盤面ルール ← 接触イベント ← 物理計算
  ↓                         ↓
得点・モード               位置・速度
  ↓                         ↓
表示・音・振動 ← 描画同期 ← 状態取得
```

物理計算は「何に接触したか」を通知するだけにする。得点や演出の判断は盤面ルール側で行う。

## 4.2 推奨ディレクトリ構成

実装開始時は、次の役割分担を基準にする。

```text
/
├─ docs/
│  ├─ IMPLEMENTATION_PLAN.md
│  └─ EXPANSION_IDEAS.md
├─ public/
│  └─ assets/
│     ├─ images/
│     ├─ audio/
│     └─ fonts/
├─ src/
│  ├─ app/            # 起動、画面遷移、全体設定
│  ├─ game/           # ゲーム進行、残り球数、ポーズ
│  ├─ physics/        # Planck.js接続、物理世界、同期
│  ├─ table/          # 盤面データ、部品生成、接触通知
│  ├─ rules/          # 得点、倍率、ミッション、モード
│  ├─ rendering/      # PixiJS描画、ライト、粒子
│  ├─ input/          # タッチ、キーボード、入力解除
│  ├─ audio/          # 効果音、音量、再生制御
│  ├─ storage/        # 設定、最高得点の端末内保存
│  ├─ debug/          # 判定表示、イベント履歴、性能表示
│  └─ ui/             # 開始、ポーズ、結果、設定画面
├─ tests/
└─ .github/workflows/
```

実際のファイル数は必要最小限から始める。初期段階で形式だけの空ファイルを大量に作らない。

## 4.3 盤面データ

盤面の形と部品を、ゲーム処理から切り離したデータで定義する。

初期の定義対象:

- 盤面サイズ
- 外周壁とレール
- 球の開始地点
- 左右フリッパー
- 発射レーン
- バンパー
- スリングショット
- 通過レーン
- 目標
- アウトレーン
- 中央の落下口
- 見えない接触センサー
- 得点と部品ID

盤面座標は画面のピクセル数ではなく、ゲーム内の共通単位で管理する。画面サイズが変わっても、球の速度や重力が変わらないようにする。

盤面データは読み込み時に検査し、ID重複、座標不足、負のサイズ、未対応部品などを早い段階で拒否する。

## 4.4 物理計算

物理計算は画面描画と分け、一定の時間間隔で進める。

初期比較:

- 1秒60回
- 1秒120回

比較項目:

- 球のすり抜け
- フリッパーの反応
- バンパー接触の安定性
- iPhoneでの処理負荷
- 画面が一時停止した後の復帰

採用値は実機試験で決める。1フレーム内の物理計算回数には上限を設け、画面復帰時に物理時間が一気に進まないようにする。

球には速度上限を設ける。ただし、通常プレイ中に頻繁に上限へ達する設定にはしない。

## 4.5 ゲーム状態

最低限、次の状態を明確に分ける。

- 起動中
- タイトル
- 発射待ち
- プレイ中
- ボール終了処理
- 次球準備
- 一時停止
- ゲーム終了
- 結果表示

状態をまたいで入力、得点、物理計算が残らないようにする。

例:

- 一時停止中は物理計算と得点を止める
- 結果画面では接触イベントを受け取らない
- 次球開始時に前の球の入力状態を破棄する

## 4.6 接触イベントと盤面ルール

物理処理は部品IDを使い、次のようなイベントを通知する。

- バンパーへ接触
- レーンを通過
- 目標へ接触
- 発射レーンを離脱
- アウトレーンへ進入
- 中央から落下
- 球が一定時間停止

盤面ルールはイベントを受けて、得点、ライト、倍率、ボーナスモードを更新する。

同じ接触が短時間に連続して通知される場合に備え、部品ごとに再得点できるまでの短い待ち時間を設定できるようにする。

## 4.7 入力

タッチ操作とキーボード操作を、共通の入力状態へ変換する。

MVPの入力:

- 画面左側を押す: 左フリッパー
- 画面右側を押す: 右フリッパー
- 発射領域を引いて離す、またはボタンを押す: 発射
- ポーズボタン: 一時停止

必須対策:

- 左右を同時に押せる
- 複数の指を個別に追跡する
- 指が画面外へ移動したときに解除する
- 画面が非表示になったときに全入力を解除する
- アプリ切り替え後に押しっぱなしを残さない
- ブラウザのスクロールや拡大操作と競合しない

## 4.8 表示

PixiJSでゲーム盤面を描画し、通常のHTMLとCSSでタイトル、設定、ポーズ、結果画面を表示する。

画面構成:

- 上部: 得点、倍率、残り球数、現在の目標
- 中央: 盤面
- 下部: iPhoneの安全領域を考慮した操作領域

物理判定用の形状と表示画像は別管理にする。

演出の優先順位:

1. 接触したことが分かる
2. 得点の大きさが分かる
3. 次に狙う場所が分かる
4. 高得点時に特別感がある

常に激しく点滅させず、重要な場面に強い演出を限定する。

## 4.9 音と振動

効果音は、最初のユーザー操作後に有効化する。

MVPの音:

- フリッパー作動
- 発射
- 壁接触
- バンパー接触
- 目標達成
- ボーナス開始
- ボール終了
- ゲーム終了

設定:

- 初期値は音なし、または初回に選択させる
- 効果音の有無を保存
- 音量を保存
- 同じ音が短時間に重なりすぎないよう制御

振動は対応端末でのみ使い、設定から無効化できるようにする。MVPでは必須にしない。

## 4.10 保存

MVPではブラウザ内へ次を保存する。

- 最高得点
- 効果音設定
- 音量
- 画面効果の強さ
- 初回説明を確認したか

保存に失敗してもプレイは続行できるようにする。

オンラインランキングはMVP後に追加する。

## 4.11 開発用確認機能

通常のプレイヤーには表示しない確認モードを用意する。

- 物理判定の形状表示
- 球の位置、速度、回転
- フリッパーの角度と入力状態
- 接触した部品ID
- 直近の得点イベント
- 現在のゲーム状態
- 物理計算回数
- 描画速度
- 停止球の検出状態

不具合報告時に、確認情報をテキストとしてコピーできる形を目標にする。

## 5. MVPのゲーム仕様

## 5.1 基本ルール

- 1ゲーム3球
- 球が中央またはアウトレーンから落ちると1球終了
- ゲーム開始直後と各球の開始直後に短いボールセーブを付ける
- ボールセーブ中に落下した場合は、残り球数を減らさず再発射する
- 3球終了後に結果画面を表示する

## 5.2 盤面部品

- 左右フリッパー: 2本
- 発射装置: 1基
- バンパー: 3個
- スリングショット: 左右1個ずつ
- 通過レーン: 3本
- 目標: 3個
- アウトレーン: 左右1本ずつ
- 中央落下口: 1か所

## 5.3 得点と倍率

初期値は仮設定とし、試遊で調整する。

- 壁接触: 原則得点なし
- バンパー: 小得点
- スリングショット: 小得点
- 通過レーン: 中得点
- 目標: 中得点
- 3レーン完成: ボーナス加算
- 3目標完成: 倍率上昇

得点の桁数は演出都合で増やさず、プレイヤーが差を理解できる範囲にする。

## 5.4 MVPのボーナスモード

3本のレーンと3個の目標をすべて完成すると、一定時間だけ得点が2倍になる。

必要な表示:

- 未達成箇所のライト
- 達成時の短い演出
- 残り時間
- 2倍になった得点の表示

ボーナス終了後は、レーンと目標の進行を初期化する。

作業を細かく分けすぎず、機能がまとまって確認できる単位で進める。

## フェーズ1: 物理動作の技術検証

実装対象:

- 最小の起動処理
- 物理世界
- 球1個
- 壁
- フリッパー1本
- タッチ入力

## 7. テスト計画

## 7.1 自動テスト

最低限、次を自動化する。

- 得点加算
- 倍率適用
- レーン完成判定
- 目標完成判定
- ボーナス開始と終了
- 接触の二重得点防止
- ボールセーブ
- 残り球数
- 3球終了
- ポーズ中の停止
- 再開始時の初期化
- 不正な盤面データの拒否

## 7.2 物理試験

- 高速の球を壁へ1,000回以上衝突させる
- バンパーへ異なる角度から衝突させる
- フリッパー先端へ高速で衝突させる
- 左右フリッパーを同時に連打する
- 球を長時間動かし続ける
- 球が静止した場合の回収処理を確認する
- 画面を非表示にして復帰する

物理計算には端末差が出る可能性があるため、自動試験だけで完了としない。

## 7.3 実機確認

主要確認端末:

- iPhone 17 Pro

補助確認端末:

- iPhone 11 Pro
- iPad Pro 2018
- PC相当のChrome自動確認

確認項目:

- 表示の見切れ
- 安全領域
- 左右同時入力
- スクロール誤動作
- 画面回転
- 音の開始制限
- アプリ切り替え
- 15分以上の連続プレイ
- 発熱と電池消費の急増

## 8. MVP完成条件

次のすべてを満たした時点でMVP完成とする。

### 8.1 物理

- 自動試験1,000回以上で、球の壁抜けが再現しない
- 球が盤面外や壁内部へ残り続けない
- フリッパーの角度と戻りが安定する
- 画面復帰時に物理時間が暴走しない

### 8.2 操作

- 左右同時入力ができる
- 指が画面外へ移動しても入力が解除される
- アプリ切り替え後に押しっぱなしが残らない
- 発射、フリッパー、ポーズが誤って同時発動しない

### 8.3 ルール

- 3球、得点、倍率、ボーナス、ゲーム終了が一貫して動く
- 一度の接触で得点が二重に入らない
- ポーズ中と結果画面で得点が進まない
- 再開始時に前回の状態が残らない

### 8.4 表示と性能

- 対象端末で盤面が見切れない
- 通常プレイ中に継続的な大きな処理落ちがない
- 15分以上の連続プレイで、操作遅延が悪化しない
- 不要になった球、演出、音が残り続けない

### 8.5 公開品質

- 型検査が成功する
- 自動テストが成功する
- 本番ビルドが成功する
- GitHub Pagesへ公開できる
- ブラウザ上で未処理エラーが出ない
- 素材と外部ライブラリの出所とライセンスが記録されている
- 既存作品の画像、音、盤面、ROM、商標を無断使用していない

## 9. GitHub運用

## 9.1 基本ルール

- `main`へ直接実装しない
- 1つのまとまった作業につき1ブランチ
- 原則としてDraft PRを作る
- 実装と無関係な変更を同じPRへ混ぜない
- 自動検査が失敗した状態で取り込まない
- 大きな依存関係追加は理由と代替案をPRへ記載する

## 9.2 推奨ブランチ名

```text
agent/physics-prototype
agent/playable-game-loop
agent/table-and-rules
agent/presentation-and-audio
agent/release-hardening
```

## 9.3 PRの確認項目

- 何を変更したか
- なぜ必要か
- プレイヤーへの影響
- 変更した仕様
- 自動検査結果
- 実機確認結果
- 残っている問題
- 使用した素材とライセンス

## 9.4 依存関係の管理

- バージョン範囲を広げすぎない
- lockファイルを保存する
- ライブラリ更新だけのPRを分ける
- 更新前後で物理試験を実行する
- 不要なライブラリを追加しない

## 10. OSSの再利用方針

既存のピンボールOSSは、主に設計の参考として利用する。

参考対象:

- Vector Pinball: 盤面データ、部品生成、物理、ルールの分離
- Mission Pinball Framework: 接触イベントからゲームモードを進める考え方
- Flutter Pinball: ゲーム、画面、音、保存を役割ごとに分ける構成
- Visual Pinball系列: 盤面データ、表示、物理、ルールの独立
- WPC-EMU: 固定時間、イベント記録、状態比較、確認画面

コードを直接コピーする場合は、対象ファイルのライセンスを個別に確認する。GPL系コードは、設計を参考にするだけとし、DOPPANのコードへコピーしない。

画像、音、フォント、盤面データは、コードのライセンスとは別に確認する。

DOPPANの自作コードはMITライセンスを推奨する。実装開始前にリポジトリへ正式なLICENSEファイルを追加する。

## 11. 実装開始前の最終決定事項

次の内容を初期値として採用する。

| 項目 | 決定内容 |
|---|---|
| 表現 | 2Dベクター調 |

| 言語 | TypeScript |
| 開発 | Vite |
| テスト | Vitest |
| 公開 | GitHub Actions + GitHub Pages |

| ライセンス | 自作コードはMITを推奨 |

テーマ、ゲーム名の表示表記、色、効果音の方向性は、物理動作の技術検証が通過した後に決定する。
