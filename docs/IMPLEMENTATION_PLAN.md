## 2. 技術構成

### 2.1 初期候補

| 用途 | 初期候補 |
|---|---|
| 実行環境 | Node.js 24.18.0 LTS |
| 言語 | TypeScript |
| 描画 | PixiJS 8.19.0 |
| 物理 | Planck.js 1.5.0 |
| 開発・ビルド | Vite 8.1.5 |
| 単体・物理試験 | Vitest 4.1.10 |
| ブラウザ試験 | Playwright Test 1.61.1 |
| 公開 | GitHub Actions + GitHub Pages |

これらは実装前の候補である。G1実装PRで互換性を確認し、正確な版を`package.json`と`package-lock.json`へ固定する。

### 2.2 TypeScript

中心処理では次を型で区別する。

- ゲーム状態
- 球、部品、ショットのID
- 入力所有者
- 物理接触イベント
- 得点イベント
- 物理変更命令
- 状態遷移要求
- 盤面、ルール、保存、クライアントの版

外部JSON、保存データ、URLパラメーターは`unknown`として受け、検査後に使う。中心処理で`any`を逃げ道にしない。

### 2.3 PixiJS

本番描画経路はWebGLとする。

- Canvasを完全な代替として保証しない
- WebGPUは正式版1.0で使わない
- `devicePixelRatio`は初期上限2
- WebGL初期化失敗時は理由を表示
- コンテキスト喪失時は物理・入力・得点を停止
- 自動復旧できない場合は白画面にせず、安全な再読み込み案内へ移る

### 2.4 Planck.js

G1の第一候補とする。

対象:

- 球
- 壁、レール
- 左右フリッパー
- 発射装置
- バンパー、スリングショット
- ゲート、センサー、落下判定

球は高速物体として扱う。

次が2調整サイクル後も未達の場合、盤面制作を止める。

- 高速衝突
- 球を受ける操作
- ショット再現性
- iPhone 11 Proでの性能
- 接触処理の安定
- 大量の個別補正なしでの操作感

見直し順:

1. 関節と接触形状
2. 限定的な接触補助
3. 球速上限と盤面形状
4. 物理方式またはエンジン
5. 作品約束から保持を外す判断

## 3. 依存方向

```text
入力・UI
   ↓
ゲーム進行・状態遷移
   ↓
ルール・ショット判定
   ↓
物理接続

物理状態 → 描画同期 → PixiJS
ゲームイベント → 表示・音・触覚
```

禁止:

- 物理からPixiJSを直接呼ぶ
- 得点ルールからHTMLを直接変更する
- UIからPlanck.jsの物体を直接操作する
- ルールへ音声ファイル名を書く
- 描画状態を得点やショット判定へ使う
- 接触コールバック中に物理世界を変更する

├─ public/
│  └─ assets/
├─ src/

│  ├─ runtime/         # TableRuntimeState、経路、ゲート
│  ├─ shots/           # 球別ショット状態機械
│  ├─ rules/           # 得点、倍率、球間進行、モード
│  ├─ rendering/       # PixiJS、表示同期、WebGL復旧
│  ├─ audio/           # 音イベント、同時再生制限
│  ├─ haptics/         # 任意の短い触覚
│  ├─ storage/         # 設定・最高得点・版移行
│  ├─ diagnostics/     # 性能、履歴、試遊レポート

├─ tests/
│  ├─ unit/
│  ├─ physics/
│  ├─ fixtures/
│  └─ e2e/

## 5. ゲームエンジンの基本規則

詳細は[ゲームエンジン設計](./ENGINEERING_ARCHITECTURE.md)に従う。

### 5.1 物理単位

- 画面ピクセルをPlanck.jsへ直接渡さない
- 盤面横幅は初期候補9物理単位
- 球、フリッパー、壁を0.1〜10単位を中心に収める
- 画面表示時だけ拡大・縮小する
- 角度は内部でラジアンを使う

### 5.2 固定時間

TPで60ステップ/秒と120ステップ/秒を比較する。

初期規則:

- 最大追いつき時間66ms
- 60ステップ/秒は最大4ステップ/描画
- 120ステップ/秒は最大8ステップ/描画
- 非表示中の時間は破棄
- 250ms以上の差は復帰・停止扱い
- 表示位置は物理状態を補間

### 5.3 接触

- 接触コールバックでは必要値だけ独自データへ複写
- contact参照を物理ステップ後まで保持しない
- 同一ステップの重複通知を除去
- 得点イベントへ一意のIDを付ける
- 物理変更は`PhysicsCommandQueue`へ予約
- ステップ終了後に得点、盤面進行、物理変更を処理

### 5.4 状態変更

- 状態は`GameStateMachine`だけが変更
- 同一ステップの遷移要求へ優先順位を設定
- 状態遷移時に入力、得点受付、音を整理
- 状態一覧だけでなく遷移表を自動試験する

## 6. 入力

### 6.1 Pointer Events

`pointerId`を押し始めた操作へ固定する。

```text
pointerId 12 → 左フリッパー
pointerId 18 → 右フリッパー
pointerId 24 → 発射装置
```

規則:

- 左右フリッパーは各1本の指だけが所有
- 指が別領域へ動いても操作を途中変更しない
- 同じ操作への二本目は無視
- 不要な三本目以降は無視
- 発射装置は発射待ちだけ所有可能
- `setPointerCapture`を明示使用
- ゲーム操作面だけ`touch-action: none`

全解除:

- `pointerup`
- `pointercancel`
- `lostpointercapture`
- `visibilitychange`
- `window.blur`
- ポーズ
- 状態変更
- 球終了
- 結果画面
- 例外時の安全停止

全解除処理は一か所へ集約する。

### 6.2 キーボード

```text
左: Z / ArrowLeft
右: / / ArrowRight
発射: Space
ポーズ: Escape
```

規則:

- `event.repeat`を新しい押下として処理しない
- `keyup`、`blur`、`visibilitychange`で解除
- 入力欄やボタン操作中はゲームキーを横取りしない
- タイトルから終了までキーボードだけで操作できる

### 6.3 入力遅延

次を別々に記録する。

- 入力イベントから物理反映まで
- 入力イベントから次の描画まで
- その画面の物理ステップ数
- 未処理時間の切り捨て

## 7. 物理と球の回復

### 7.1 球

持つ情報:

- ID
- 位置、速度、回転
- 所属状態
- 最後の安全状態
- 最後の有効移動時刻
- 再配置理由

正式版1.0は同時一球とする。

### 7.2 左右フリッパー

設定:

- 休止角度、最大角度
- 上昇速度、復帰速度
- 最大トルク
- 左右区分
- 入力状態

確認:

- 根元と先端で球筋が変わる
- 左右同時入力
- 連打で角度が壊れない
- 球が内部へ潜り込まない
- 球を受けて狙い直す余地がある

保持を正式版必須に残すかは[中心体験・表現計画](./CORE_EXPERIENCE_PLAN.md)の分岐で決める。

### 7.3 安全位置

毎フレーム無条件に更新しない。

更新条件:

- 盤面内
- 落下センサー外
- 不正な重なりなし
- 非有限値なし
- 球速が安全上限内
- ゲート内部ではない
- 連続3物理ステップ以上正常

再配置前に球を置く空間があるか確認する。同じ位置で異常が再発した場合は、その位置を無効化する。

システム起因の回復では原則として残り球を減らさない。

## 8. 発射装置

TPで比較する。

- 引いて離す
- 長押しして離す

採用条件:

- 盤面を隠しすぎない
- 最小、中間、最大の三段階を再現できる
- フリッパーと誤入力しない
- 基本スキルショットへ使える
- 初見で理解できる

攻略価値がない、または初見理解を大きく損なう場合は固定発射へ簡略化する。

## 9. 盤面データと実行状態

### 9.1 TableDefinition

変更しない初期定義。

- `schemaVersion`
- `tableVersion`
- `physicsScale`
- 盤面範囲
- 球開始位置
- fixture、joint、sensor
- ショット、経路
- 実行部品定義

### 9.2 TableRuntimeState

プレイ中に変わる状態。

- 接続済み経路
- ゲート開閉
- 有効ショット
- 蓄積値
- 覚醒段階

### 9.3 RuleState

- 得点、残り球
- 球をまたぐ恒久進行
- 基本倍率、一時倍率
- コンボ
- クライマックス準備
- 現在モード

### 9.4 検査

実行前に次を拒否する。

- ID重複
- 必須座標不足
- 0以下の大きさ
- 未対応部品
- 盤面外の重要部品
- 存在しない参照
- 落下口なし
- 初期球と部品の重なり
- 不正なフリッパー角度
- 重複ショットID
- 不正な経路参照
- 対応外のschemaVersion

正式版1.0で盤面が1枚の間は、重い実行時検査ライブラリを増やさず、TypeScriptの独自検査関数を第一候補とする。

## 10. ショット判定

一つのセンサー通過だけで成功にしない。

球ごと・ショットごとに次の状態を管理する。

```text
Idle → Entered → Validated → Completed → Cooldown → Idle
```

必要に応じて使う条件:

- 入口通過
- 進入方向
- 出口通過
- 通過順序
- 制限時間
- 最低速度
- 同一球内の重複防止
- 盤面状態による有効・無効

球終了、再開始、盤面版変更で途中状態を消す。

## 11. 表示・音・アクセシビリティ

表現の正本は[中心体験・表現計画](./CORE_EXPERIENCE_PLAN.md)とする。

技術上の必須:

- 球を最優先で表示
- 高速時の短い軌跡
- 強い発光でも球を隠さない
- 色だけに依存しない目標
- 音なしでも情報が欠けない
- 触覚なしでも正常動作
- 点滅、粒子、揺れを軽減可能
- 高コントラスト
- メニューと結果をキーボード操作可能

WebGL喪失時は、自動復旧または安全停止のどちらかを成立させる。

## 12. 保存と共有

### 12.1 保存

- 最高得点
- 主要得点内訳の自己最高
- 音・画面効果・高コントラスト・軌跡設定
- 初回案内
- 保存版

方針:

- 永久保持を保証しない
- 保存失敗でもプレイ継続
- プライベートブラウズ試験
- 読み込み不能時は安全な初期値
- 進行中ゲームは保存しない

### 12.2 共有

1. Web Share API
2. 結果テキストをクリップボードへコピー
3. URLと結果文を画面表示

共有失敗をゲーム失敗にしない。

## 13. 診断・試遊レポート

GAまでに端末内で生成する。

出力:

- 読みやすいテキスト
- 必要に応じて`playtest-report.json`

含める:

- コミットSHA、各版

- ショット試行・成功

含めない:

- 氏名
- 連絡先
- 永続的な端末識別子
- 自動送信

初期上限:

- 試遊レポート256KB
- 状態遷移履歴128件
- 入力履歴512件
- エラー履歴64件

利用者が内容を確認してコピーする。

技術試作だけを扱う。

確認すること:

> iPhoneのタッチで球を発射し、左右のフリッパーで受け、狙って安全ショットへ打ち返せること。接触処理、固定時間、入力解除、PRプレビュー、自動ブラウザ試験も同時に成立させる。
