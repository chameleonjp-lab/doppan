## 1. この文書の役割

本書は、DOPPANをGitHub Pagesで確認・公開する際の正本である。

次を一つの実装担当者の判断へ任せない。

- 完成前の確認ページをどこへ置くか
- `main`への取り込みと一般公開をどう分けるか
- 完成までURLを案内しない方針をどう守るか
- 端末へ保存できる非個人設定をどう分けるか
- ゲーム記録、個人アカウント、外部分析を実装しない方法
- 外部フォークのpull requestを自動公開しない方法
- GitHub Actionsへ与える権限
- 本番公開と開発用公開が競合しない方法
- GitHub Pagesが公開URLであることの限界
- GitHub PagesとGitHub Actionsの規約境界
- 容量と帯域が無料運用の範囲を超える前に止める方法

CIとブラウザ試験の詳細は[自動試験・確認ページ計画](./TEST_AND_PREVIEW_PLAN.md)を参照する。

データ、アカウント、外部通信について本書と他文書が衝突する場合は、[データ非保存・GitHub運用方針](./DATA_AND_HOSTING_POLICY.md)を優先する。

## 2. 基本方針

### 2.1 GitHub Pagesを使用する

DOPPANの確認ページと正式版はGitHub Pagesで配信する。

ただし、完成前と完成後を同じ意味で扱わない。

- 完成前: **未告知の開発確認ページ**
- G7公開承認後: **正式版の一般公開ページ**

正式版1.0は、HTML、CSS、JavaScript、画像、音声を配る静的サイトとする。ゲームの物理、得点、進行はプレイヤーのブラウザ内で動かす。

### 2.2 完成まではURLを案内しない

完成までは次を行わない。

- READMEやリポジトリ説明へゲームURLを掲載
- カメレオンJPの公開サイトからリンク
- SNS、チャット、記事でURLを案内
- 検索エンジン向けサイトマップへ掲載
- 公開用画像や動画から確認URLへ誘導
- pull request本文へ確認URLを恒常的に転載

確認URLは、ユーザー本人がGitHub ActionsのSummaryなどから開くためだけに使用する。

### 2.3 非公開ではない

GitHub Pagesは公開URLである。

URLを案内しなくても、次を完全には防げない。

- URLを推測される
- GitHub Actionsや公開リポジトリから構成を調べられる
- 検索除外設定が無視される
- 第三者が直接アクセスする

そのため、本計画では「秘密のテスト環境」「アクセス制限された非公開環境」とは表現しない。

完成前に置いてよいものは、第三者に見られても安全な開発版だけとする。

### 2.4 データを持たない

正式版1.0では次を持たない。

- 個人アカウント
- ログイン
- 名前登録
- 永続的な利用者識別子
- 得点、最高得点、戦績、履歴、プレイ回数の保存
- ランキング
- 外部分析
- 外部データベース
- 決済

一回のゲーム状態はブラウザのメモリだけで保持する。端末内へ保存できるのは、音、画面効果、高コントラスト、初回案内などの非個人設定だけとする。

## 3. GitHub Pages規約への適合判断

### 3.1 公式資料

2026年8月10日時点で次を確認した。

- GitHub Pages limits: https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits
- GitHub Terms for Additional Products and Features: https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features

追加機能規約の現行版は2026年4月27日発効である。

### 3.2 現在のDOPPAN

GitHub Pagesは、静的ページを、主として個人または組織のプロジェクトを紹介する用途で提供している。

現在のDOPPANは次の条件を満たす。

- 一つの公開リポジトリに対応する無料ブラウザゲーム
- 静的ファイルのみ配信
- 商取引なし
- 決済なし
- 商用Software as a Serviceではない
- 個人アカウントなし
- 利用者データ収集なし
- サーバー上のゲーム処理なし
- GitHub Actionsは開発、試験、ビルド、配置だけ

この構成は、GitHub Pagesが想定する静的なプロジェクト公開の範囲に入る可能性が高い。

ただし、GitHubによる最終判断を保証しない。疑義がある場合、G7前にGitHub Supportへ確認する。

### 3.3 Pagesで禁止する機能

GitHub Pagesをオンライン事業、電子商取引、商取引を主目的とするサイト、商用SaaSの無料ホストとして使わない。

正式版1.0では次を禁止する。

- 有料会員
- 有料アイテム
- 商品購入
- 決済情報送信
- 商取引を主目的とする導線
- 企業向け有料サービスとしての提供
- パスワードやカード番号を扱う画面

寄付やクラウドファンディングの導線はGitHubの許容例に含まれるが、DOPPAN正式版1.0の必須機能にしない。

### 3.4 Actionsで禁止する用途

GitHub Actionsを次へ使わない。

- ゲーム中の要求を受けるAPI
- サーバーレスアプリの代用
- 定期的なランキング集計
- 常時稼働処理
- 配信網の代用
- リポジトリの開発、試験、配置と関係しない処理

Actionsの実行は、依存取得、型検査、静的検査、単体・物理・ブラウザ試験、ビルド、容量確認、承認後のPages配置に限定する。

## 4. 容量と帯域

### 4.1 GitHubの公表値

- Pages公開サイト: 1GB以内
- 月間帯域: 100GBの柔軟な上限
- Pages配置: 10分で時間切れ
- Pages標準ビルド: 1時間10回の柔軟な上限
- カスタムGitHub Actionsでビルド・公開する場合、標準Pagesビルド回数の上限は適用対象外
- レート制限が適用される場合があり、反復時はHTTP 429を受ける可能性がある

100GBは契約上の保証枠ではない。超過時は配信停止、GitHubからの連絡、別ホストの案内があり得る。

### 4.2 DOPPANの運用想定

- 1日100人
- 1日200プレイ
- 月約6,000プレイ
- 初回転送3MB以内
- 遅延素材を含む総容量10MB以内

毎プレイで全10MBを読み直す厳しい条件:

```text
10MB × 200プレイ × 30日 = 約60GB／月
```

公表されている100GBを下回るが、余裕を使い切らない。

### 4.3 内部停止線

次のいずれかに該当したら、新しい素材追加と正式公開更新を止める。

- 初回転送3MBを継続的に超える
- 総容量10MBを超える
- 月間転送見積もり70GBを超える
- GitHubから負荷、帯域、利用方法について警告を受ける
- HTTP 429が反復する
- 公開サイトが1GBへ近づく
- 動画、大容量音声、ユーザー投稿を追加する計画が出る

停止後は、素材削減、機能削減、別ホスト移行の順で再検討し、ユーザー本人の承認を得る。

DOPPAN自身ではプレイ人数や通信量を追跡しない。GitHubが管理画面で提供する範囲の情報と、ファイル容量による安全側見積もりを使う。

## 5. GitHub Pagesの構成

### 5.1 G7承認前

G1-Aで、GitHub Pagesの成果物を次の構成に固定する。

```text
/
├─ index.html                 # 開発中を示す静的な案内だけ
├─ robots.txt                 # 全体を検索対象外として依頼
└─ _preview/
   └─ current/                # 現在確認中の信頼済みブランチ1件
```

本番ルートには未完成ゲームを配置しない。

開発確認ページは同時に一件だけとする。複数pull requestの成果物を同じPages成果物へ並行して統合しない。

### 5.2 G7承認後

正式公開時は次へ切り替える。

```text
/
├─ index.html                 # 正式版
├─ assets/
├─ robots.txt                 # 正式な公開方針へ更新
└─ _preview/                  # 原則として公開成果物へ含めない
```

正式公開後は、同一オリジンに開発版を常設しない。

正式版公開後に確認ページが必要になった場合は、次のいずれかを改めて承認する。

- 別オリジンを持つ確認環境
- GitHub Pages上での信頼済み・短時間・手動確認
- 確認ページを使わず、CI成果物と実機ローカル確認を組み合わせる方法

外部貢献者のコードを同一オリジンへ公開する方式は採用しない。

## 6. 確認ページの対象

### 6.1 公開できるブランチ

自動または手動で確認ページへ出せるのは、次をすべて満たすブランチだけとする。

- `chameleonjp-lab/doppan`内のブランチ
- ユーザー本人または承認済み実装担当が作成
- 外部フォークではない
- 秘密情報を含まない
- 型検査、単体試験、物理試験、ビルドが成功
- 確認ページ用の環境表示を含む
- 個人アカウント、記録保存、外部分析、決済を含まない

### 6.2 公開しないpull request

次はCIだけ実行し、Pagesへ出さない。

- 外部フォークからのpull request
- 不明な作成者のブランチ
- Dependabotなど依存更新だけのpull request
- 権限変更や公開ワークフロー自体を変更する未承認pull request
- 秘密情報を必要とするもの
- P0、P1相当の既知問題があるもの
- アカウント、記録送信、外部分析、決済を無断で追加するもの

### 6.3 `pull_request_target`の禁止

未信頼コードを実行する目的で`pull_request_target`を使わない。

外部pull requestのコードへ書き込み権限、Pages公開権限、秘密情報を渡さない。

## 7. `main`と正式公開の分離

### 7.1 `main`への取り込み

`main`への取り込みでは次だけを行う。

- 依存取得
- 型検査
- 静的検査
- 単体試験
- 物理試験
- ブラウザ試験
- 本番形式のビルド確認
- 容量確認

**`main`への取り込みだけでは正式版を公開しない。**

G1、G2、GA、VS、CCBの未完成版を本番ルートへ自動配置しない。

### 7.2 開発確認ページ

開発確認ページへの配置は、信頼済みブランチだけを対象とする専用ワークフローで行う。

G1-Aの初回構築では、専用内部ブランチ`agent/g1a-technical-foundation`のpush時だけ起動する。同じワークフロー内で自動試験を再実行し、成功した成果物だけを配置する。

初回配置前にGitHub Environment `github-pages`へユーザー本人の必須reviewerと、bootstrap push用`agent/g1a-technical-foundation`および手動更新・cleanup用`main`だけを許可するdeployment branch ruleを設定する。その確認後にだけRepository variable `DEVELOPMENT_PREVIEW_ENABLED=true`を設定する。

ブランチ上のworkflow自身が変更可能であるため、このEnvironment保護と明示スイッチを初回bootstrapの前提とする。設定を確認できない場合は、検査成果物までで停止し、Pages配置を完了扱いにしない。

`main`へ専用ワークフローを取り込んだ後は、`workflow_dispatch`で同一リポジトリ内の信頼済みrefと表示名を明示して更新できる。G1-A / G1-Bの専用内部ブランチをallowlistし、checkoutしたSHAが対象ブランチの現在tipと一致する場合だけ実行する。`refs/pull/*`とallowlist外のSHAは拒否する。

確認ページは一件だけなので、後から実行された承認済みビルドで置き換える。

終了処理は`workflow_dispatch`専用の別ワークフローで、開発中案内と`robots.txt`だけを含む成果物へ全体を置き換える。G1-Aマージ後に実際の削除結果を確認する。

### 7.3 正式版公開

正式版公開はG7通過後、次のいずれかで行う。

- `workflow_dispatch`による手動実行
- GitHub Environment `production`の承認付き実行

公開するコミットSHAを明示し、公開後に版を付ける。

正式公開を通常のpushやpull requestマージへ連動させない。

## 8. 非個人設定とデータ境界

### 8.1 設定キー

端末内保存を許可するのは非個人設定だけとする。

```text
doppan:development-preview:settings:v1
doppan:production:settings:v1
doppan:test:settings:v1
```

ビルド時に次を埋め込む。

```text
APP_ENV=development-preview | production | test
BUILD_SHA=<commit sha>
BUILD_SOURCE=<pull request or release>
```

開発版は通常処理で本番設定キーを読まない、書かない。

### 8.2 設定へ入れてよいもの

- 音の有無と音量
- 点滅、粒子、揺れ、軌跡の軽減
- 高コントラスト
- 初回案内の表示設定

### 8.3 設定へ入れてはいけないもの

- 氏名、メール、パスワード
- 利用者ID、端末ID、端末指紋
- 得点、最高得点、得点内訳
- 戦績、履歴、プレイ回数、日時
- 球数、盤面進行、倍率、コンボ
- リプレイ、ゴースト

一回のゲーム状態はブラウザのメモリだけに置く。再読み込み、タブ終了から復元しない。

### 8.4 同一オリジンの限界

GitHub Pagesの本番ルートと確認ページは同じオリジンを共有する。

設定キーを分けても、同じオリジンで実行されるJavaScriptは技術的には別キーへアクセスできる。

このため、次を必須とする。

- G7前は本番ゲームと本番設定を配置しない
- 確認ページへ出すコードは同一リポジトリ内の信頼済みブランチだけ
- 外部pull requestを確認ページへ出さない
- G7後は確認ページを原則停止
- 将来外部貢献を受ける場合は別オリジンへ移行

### 8.5 設定の安全な更新

設定は次の順で行う。

1. 一時キーへ書く
2. 読み戻す
3. データ形式と禁止フィールドを検査する
4. 正式キーへ書く
5. 一時キーを削除する

書き込み失敗でもゲームを続ける。破損した値を正式値として採用しない。

既存の汎用保存部品は設定専用へ狭める。ゲーム記録用の保存APIとして利用可能なまま正式版へ残さない。

## 9. 検索除外と未告知表示

G7前は次を行う。

- `robots.txt`で全体の巡回停止を依頼
- `meta name="robots" content="noindex,nofollow,noarchive"`
- 本番ルートから確認ページへリンクしない
- 確認ページにも同じ`noindex`指定
- OGPや検索向け説明を設定しない
- 画面に「開発確認版」「一般公開前」を表示
- PR番号または確認対象名とコミットSHAを表示

これらは検索除外の依頼であり、アクセス制限ではない。

## 10. GitHub Actionsの権限

### 10.1 既定権限

ワークフロー全体の既定は次とする。

```yaml
permissions:
  contents: read
```

### 10.2 CI

CIは読み取り権限だけで実行する。

- リポジトリへ書き込まない
- Pagesへ公開しない
- 秘密情報を必要としない

### 10.3 Pages公開

Pages公開ジョブだけに必要な権限を与える。

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

必要以上の`contents: write`、`pull-requests: write`、`actions: write`を与えない。

### 10.4 Actionsの固定

第三者Actionは完全なコミットSHAへ固定する。

バージョンタグだけを信頼しない。更新は独立した依存更新として確認する。

### 10.5 Environment

次を分ける。

- `github-pages`: G1-A / G1-Bの開発確認枠。ユーザー本人の必須reviewerと、bootstrap push用`agent/g1a-technical-foundation`および手動更新・cleanup用`main`のみを許可する制限を設定。確認後にだけ`DEVELOPMENT_PREVIEW_ENABLED=true`とする。内容refのG1-A / G1-B allowlistはワークフロー内で別に検査する
- `production`: G7後の正式公開だけ

`production`はG7まで使用しない。正式公開時はユーザー本人の承認を必要とする。

## 11. 同時実行

### 11.1 CI

同じpull requestでは古いCIを中止する。

```text
ci-pr-<番号>
```

### 11.2 開発確認ページ

確認ページは一件だけなので、全pull requestで共通のグループを使う。

```text
pages-development-preview
```

新しい承認済み配置が始まったら、古い配置処理を中止する。

### 11.3 正式公開

正式公開は別のグループを使う。

```text
pages-production
```

開発確認ページと正式公開を同時実行しない。

## 12. GitHub Actionsのジョブ分離

GitHubホスト型ランナーでは、ジョブごとに環境が分かれることを前提にする。

`install`ジョブで作った`node_modules`が別ジョブへ自動共有されるとは考えない。

実装済みの構成:

- 各ジョブで`npm ci`
- npmキャッシュで取得を短縮
- ビルド成果物だけArtifactで渡す
- `node_modules`全体をArtifactで渡さない

G1-Aでは、品質検査を一ジョブにまとめ、ブラウザ検査をChromium / WebKitの行列に分ける。実行時間が許容範囲を超えた場合だけ、次を再検討する。

- 型検査・静的検査・単体試験を一つのジョブへまとめる
- 複数ジョブでそれぞれ`npm ci`する

Actionsを定期的な本番処理や利用者要求への応答に使わない。

## 13. 開発確認ページの切り替えと削除

### 13.1 更新

確認ページを更新する時は、Pages成果物全体を再構築する。

G7前の成果物には必ず次を含める。

- 開発中のルート案内
- `robots.txt`
- 現在の確認ページ1件

他のpull request成果物を保持・統合する処理は作らない。

### 13.2 pull request終了時

pull request終了時は、確認ページを削除した成果物を再配置するか、次の確認対象へ置き換える。

G1-Aを実装したpull request自身の終了後処理は、マージ後に確認し、結果を次のPRまたは制作状況へ記録する。

一つのpull request内だけで「終了後削除まで完全確認済み」とは扱わない。

## 14. G1-Aの合格条件

- CIとPages公開の権限が分離
- 外部フォークではPages公開ジョブが実行されない
- `pull_request_target`でPRコードを実行しない
- 開発確認ページをiPhone Safariで開ける
- 本番ルートには未完成ゲームを置かない
- ルートと確認ページに`noindex`
- 開発確認ページへ環境名とコミットSHAを表示
- 開発版と本番版の非個人設定キーが分離
- 得点、履歴、回数、名前、識別子の保存がない
- 外部分析と外部データベース通信がない
- `main`への取り込みだけでは正式版を公開しない
- 正式公開は手動承認が必要
- GitHub Actionsの権限が必要最小限
- 第三者Actionを完全なコミットSHAへ固定
- Actionsを開発、試験、ビルド、配置以外に使わない
- URLを案内しない方針がREADME、公開サイト、SNS運用と一致

---

## 15. G7正式公開時の確認

- ユーザー本人が一般公開を承認
- 正式版コミットSHAを固定
- 正式版ルートへゲームを配置
- 開発確認ページを公開成果物から除外
- `robots.txt`とOGPを正式公開用へ変更
- production用の非個人設定キーを使用
- 公開URL、操作説明、対応環境を確認
- 直前成果物へ戻せることを確認
- URLを初めて外部へ案内する範囲を決定
- GitHub PagesとGitHub Actionsの最新規約を公式資料で再確認
- 静的、非商取引、決済なし、アカウントなし、無収集を確認
- Actionsが開発、試験、ビルド、配置だけであることを確認
- 公開サイトが1GB未満
- 初回3MB、総容量10MBの目標内
- 月間転送見積もり70GB以下
- 規約判断に疑義があればGitHub Supportへ確認

---

## 16. 中止条件

次の場合はPages公開処理を止める。

- 本番ルートが開発版で上書きされる可能性
- 外部pull requestが公開権限を得る
- 開発版が本番設定キーを読み書きする
- 設定へ得点、履歴、回数、名前、識別子が混入する
- 外部データベース、認証、分析、ランキング通信が無断で追加される
- 決済、商取引、商用SaaS化が追加される
- Actionsが実行時API、サーバーレス処理、定期集計、配信網に使われる
- Pages公開に不要な書き込み権限が必要
- 秘密情報をPages成果物へ含める必要がある
- 同時実行で成果物の出所を特定できない
- 公開コミットSHAを画面で確認できない
- G7前に一般公開用のリンクが掲載される
- 月間転送見積もり70GB超、HTTP 429反復、GitHub警告
- 公開サイトが1GBへ近づく
- GitHub PagesまたはActionsの規約変更で適合を確認できない

中止時はCIだけを残し、機能削減または公開方式を再設計する。自動的に別サービスを追加せず、ユーザー本人の承認を得る。
